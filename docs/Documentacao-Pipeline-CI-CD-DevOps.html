1. Sumário executivo e visão geral

Este runbook descreve, de ponta a ponta, como o backend da aplicação Achados & Perdidos (Rock in Rio) é construído, testado, auditado e implantado automaticamente pelo GitLab CI/CD. O objetivo é permitir que qualquer pessoa da equipe DevOps execute, diagnostique e evolua o pipeline sem depender de conhecimento tácito.

  • 4 estágios sequenciais: build → test → security → deploy.
  • 2 ambientes por branch: develop (dev) e main (produção).
  • 3 scanners de segurança: Trivy (SCA), Semgrep (SAST), Gitleaks (segredos).
  • 1 Dockerfile multi-stage: base → test → build → runtime.

1.1 Fluxo macro do pipeline

git pushBUILDTESTSECURITYDEPLOY
develop / main dispara o pipelinebuild + extrai app.jarMySQL efêmero + mvn testSCA/SAST/Secrets — paralelo, não bloqueia*rsync + compose (dev ou prod)

* Os jobs de segurança rodam com allow_failure: true — são visíveis mas não bloqueiam o deploy até que a equipe faça a primeira triagem de findings (ver §8).

1.2 Princípios de design adotados

  • Gate de teste real: os testes de integração dependem de um MySQL de verdade. Sem banco, a suíte é pulada (assumeTrue) e o gate não validaria nada — por isso o CI sobe um MySQL efêmero antes de testar.
  • Build reprodutível e offline no SCA: o Trivy escaneia o fat-jar já construído, sem re-resolver o Maven Central (evita rate-limit HTTP 429).
  • Deploy imutável por commit: cada imagem é etiquetada com ci-${CI_COMMIT_SHORT_SHA}, permitindo rastreabilidade e rollback.
  • Segurança por camadas (OWASP): SCA (A06), SAST (A05/A08), secret scanning, além de rate-limiting, JWT com fail-fast e CORS restritivo na aplicação.
  • Isolamento por ambiente: resource_group serializa deploys concorrentes por ambiente, evitando corrida entre pipelines.

3. Pré-requisitos de infraestrutura

3.1 GitLab Runner

Todos os jobs declaram tags: [deploy]. É obrigatório existir ao menos um runner registrado com essa tag, com acesso ao Docker daemon.

  • Executor: Shell ou Docker com socket montado — o pipeline invoca docker build, docker run, docker compose diretamente.
  • Imagem default dos jobs: docker:24-cli com pull_policy: if-not-present.
  • Docker Engine + plugin Compose v2 (o pipeline usa docker compose, não docker-compose).
  • Localização: o mesmo runner que testa também faz o deploy — precisa enxergar /opt/rockinrio-backend na VPS e o MySQL de produção.
  • Rede: acesso de saída à internet (Trivy DB, Semgrep, Gitleaks, MySQL, Temurin, Maven Central).
Por que o runner é local à VPS. O template de deploy faz rsync do repositório para /opt/rockinrio-backend e sobe o compose na própria máquina do runner. Ou seja, o runner com a tag deploy deve rodar no servidor de destino (ou ter diretório/daemon compartilhados). O stage test usa --network host, pressupondo runner Linux com host networking.

Fail-fast de segredos. Em application.properties, app.jwt.secret e app.resource-id.secret não têm valor default. Se o .env não os fornecer, a aplicação não inicia — o container entra em loop de restart. Sempre validar o .env antes de subir.

4.3 Como o segredo NÃO vaza no CI

  • O .env é excluído do rsync e do contexto de build (.dockerignore) — nunca entra na imagem.
  • Gitleaks escaneia o histórico e a árvore; .gitleaks.toml mantém allowlist só para placeholders de exemplo.
  • Credenciais de produção devem viver como CI/CD variables mascaradas/protegidas no GitLab, ou diretamente no .env do servidor.

5. Anatomia do pipeline — .gitlab-ci.yml

5.1 Estágios e ordem de execução

stages:
  - build     # 1. Constrói a imagem e extrai o fat-jar
  - test      # 2. Gate de testes com MySQL efêmero
  - security  # 3. SCA + SAST + secret scanning (paralelo)
  - deploy    # 4. rsync + docker compose up (dev/prod)

5.2 Regras de branch (quando o pipeline roda)

Uma âncora YAML reutilizável restringe a execução às branches main e develop. Qualquer outra branch (feature, hotfix) não dispara build/test/security.

.branch_main_develop: &branch_main_develop
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
    - if: $CI_COMMIT_BRANCH == "develop"

6. Stage BUILD — imagem e extração do fat-jar

build:
  stage: build
  tags: [deploy]
  <<: *branch_main_develop
  script:
    - docker build -t "${IMAGE_CI}" .
    # Extrai o fat-jar para o SCA (Trivy) escanear offline
    - docker rm -f "ci-extract-${CI_JOB_ID}" >/dev/null 2>&1 || true
    - docker create --name "ci-extract-${CI_JOB_ID}" "${IMAGE_CI}"
    - docker cp "ci-extract-${CI_JOB_ID}:/app/app.jar" ./app.jar
    - docker rm -f "ci-extract-${CI_JOB_ID}" >/dev/null 2>&1 || true
  artifacts:
    paths: [ app.jar ]
    expire_in: 1 hour
  1. docker build executa o Dockerfile até o estágio final (runtime), produzindo rockinrio-backend:ci-<sha>. Nesse processo o estágio build roda mvn -DskipTests package, gerando target/app.jar.
  2. Um container temporário é criado (não iniciado) só para copiar o artefato de dentro dele.
  3. docker cp extrai /app/app.jar para o workspace do CI.
  4. O container temporário é removido; o app.jar vira artefato (validade 1h) consumido pelo SCA.
Por que extrair o jar? O Trivy escaneia o fat-jar offline — todas as dependências já estão embarcadas. Isso evita re-resolver o Maven Central (HTTP 429), tornando o SCA determinístico e rápido.

7. Stage TEST — MySQL efêmero e gate real

test:
  stage: test
  tags: [deploy]
  needs: [build]
  variables:
    IT_MYSQL_PORT: "13306"  # 3306 já usada pelo banco da VPS
  script:
    - docker run -d --name "it-mysql-${CI_JOB_ID}" -e MYSQL_ALLOW_EMPTY_PASSWORD=1
        -e MYSQL_DATABASE=achados_perdidos_it -p ${IT_MYSQL_PORT}:3306 mysql:8.0
        --default-authentication-plugin=mysql_native_password
    - for i in $(seq 1 40); do docker exec ... mysqladmin ping ... && break; sleep 2; done
    - docker build --target test --network host
        --build-arg TEST_DB_URL="jdbc:mysql://127.0.0.1:${IT_MYSQL_PORT}/achados_perdidos_it?..."
        -t "rockinrio-backend-test:${CI_COMMIT_SHORT_SHA}" .
  after_script:
    - docker rm -f "it-mysql-${CI_JOB_ID}" >/dev/null 2>&1 || true

A base de testes (IntegrationTestBase) usa assumeTrue(canConnect(), …) no @BeforeAll. Sem banco alcançável, os testes de integração são pulados silenciosamente — o gate ficaria verde sem validar nada. Por isso o CI sobe um mysql:8.0 descartável na porta 13306, aguarda via mysqladmin ping (até 40×2s = 80s), roda docker build --target test (dispara mvn -B test) com --network host, e remove o MySQL no after_script.

Este é o gate bloqueante. Se qualquer teste falhar, o docker build --target test retorna erro e o stage test falha, impedindo o deploy (que depende de test). É o principal portão de qualidade do pipeline.

8. Stage SECURITY — SCA, SAST e secret scanning

Três jobs rodam em paralelo, todos com needs: [build] e allow_failure: true. São uma "avaliação contínua de risco": ficam visíveis (vermelhos quando há achados) mas não bloqueiam o deploy até a triagem inicial.

8.1 SCA — Trivy (A06)

sca_dependencias:
  image: aquasec/trivy:latest
  cache: { key: trivy-db, paths: [ .trivycache/ ] }
  script:
    - trivy fs --scanners vuln --severity HIGH,CRITICAL --exit-code 1 --format table app.jar
  allow_failure: true

8.2 SAST — Semgrep (A05/A08)

sast_semgrep:
  image: semgrep/semgrep:latest
  script:
    - semgrep scan --error --config "p/java" --config "p/secrets" --config "p/owasp-top-ten"
        --exclude-rule dockerfile.security.missing-user.missing-user .
  allow_failure: true

A regra missing-user (container como root) é excluída por ora: o compose faz bind-mount de ./arquivos, e rodar como não-root exigiria ajustar permissões do volume no servidor.

8.3 Secret scanning — Gitleaks

secret_detection:
  image: zricethezav/gitleaks:latest
  script:
    - gitleaks detect --source . --config .gitleaks.toml --redact --verbose --exit-code 1
  allow_failure: true
8.4 Como promover um job a GATE bloqueante. Após a primeira triagem, remova allow_failure: true do job. A partir daí, um HIGH/CRITICAL faz o pipeline falhar. Recomenda-se começar por secret_detection (tolerância zero) e depois SCA.

9. Stage DEPLOY — publicação em dev e produção

.deploy_template: &deploy_template
  stage: deploy
  before_script:
    - # instala rsync (apk/apt) se ausente
  script:
    - mkdir -p "${DEPLOY_DIR}"
    - rsync -a --delete --no-owner --no-group
        --exclude .env --exclude .git --exclude target
        --exclude arquivos --exclude paineladmin --exclude portalpublico ./ "${DEPLOY_DIR}/"
    - cd "${DEPLOY_DIR}"
    - test -f .env || (echo "ERRO - crie .env..." && exit 1)
    - docker compose down --remove-orphans --timeout 30 || true
    - docker rm -f rockinrio-backend 2>/dev/null || true
    - docker compose up -d --build --remove-orphans --force-recreate
    - docker compose ps
    - IMAGE_CI="${IMAGE_CI}" sh scripts/ci-docker-cleanup.sh

O rsync sincroniza o repositório para /opt/rockinrio-backend (excluindo .env, uploads, build local e frontends), valida a presença do .env, para a stack atual, sobe a nova versão com --build --force-recreate, imprime docker compose ps e executa a limpeza.

Estratégia de indisponibilidade. O deploy usa down → up --build: há uma janela de downtime enquanto a imagem é reconstruída e o container reinicia. Planeje deploys em horários de baixo tráfego. 10. Dockerfile multi-stage, runtime e health check

FROM maven:3.9-eclipse-temurin-25 AS base
WORKDIR /app
COPY pom.xml .
RUN mvn -B dependency:go-offline          # camada cacheável de dependências
COPY src ./src

FROM base AS test                         # usado só no stage "test" do CI
ARG TEST_DB_URL                           # falha aqui = gate de teste vermelho
ENV TEST_DB_URL=${TEST_DB_URL} ...
RUN mvn -B test

FROM base AS build                        # gera target/app.jar
RUN mvn -B -DskipTests package

FROM eclipse-temurin:25-jre-alpine        # runtime enxuto (JRE only)
WORKDIR /app
ENV SERVER_PORT=8080
COPY --from=build /app/target/app.jar app.jar
RUN mkdir -p arquivos
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=5s --start-period=45s --retries=3 \
  CMD wget -q -O - "http://127.0.0.1:${SERVER_PORT}/actuator/health" | grep -q '"status":"UP"' || exit 1
CMD ["java", "-jar", "app.jar"]

O uso de JRE Alpine no estágio final reduz drasticamente o tamanho e a superfície de ataque (sem Maven, sem JDK, sem código-fonte). O wget usado no health check vem do busybox da própria imagem Alpine.

10.3 Health check rev. 1.1

O container expõe um endpoint de saúde dedicado, consumido pelo Docker/orquestrador e por eventual load balancer:

  • Endpoint: GET /actuator/health (Spring Boot Actuator). Retorna {"status":"UP"} quando aplicação e dependências essenciais (incl. datasource) estão saudáveis; 503 caso contrário.
  • Exposição restrita: apenas o endpoint de saúde é publicado (include limitado a health no Actuator), sem detalhes (show-details = never) — nenhuma informação de diagnóstico vaza, alinhado ao relatório de segurança (M-04 / A05). Liberado sem autenticação no SecurityConfig; os demais endpoints de management não são expostos. Configuração em application.properties.
  • Definição: HEALTHCHECK no Dockerfile (imagem auto-descritiva) e bloco healthcheck no compose (runtime da VPS). start-period de 45s cobre o boot da JVM/Spring; 3 tentativas de 30s antes de marcar unhealthy.
  • Efeito operacional: docker compose ps passa a exibir STATUS = healthy e docker inspect … {{.State.Health.Status}} (§15.1) retorna o estado real — antes retornava vazio por não haver health check definido.

Validação manual: curl -fsS http://127.0.0.1:8203/actuator/health na VPS deve retornar {"status":"UP"} com HTTP 200.

11. Nginx, Cloudflare e exposição da API

Referência em deploy/nginx/api_rockinrio.xpto.com.br.conf. Instalar em /etc/nginx/sites-available/ com symlink em sites-enabled/.

server {
  listen 80;
  server_name api_rockinrio.xpto.com.br;
  location / {
    proxy_pass http://127.0.0.1:8203;                         # HOST_PORT do container (prod)
    proxy_http_version 1.1;
    proxy_set_header Host              api-rockinrio.xpto.com.br;  # hífen: Tomcat rejeita "_"
    proxy_set_header X-Forwarded-Host  api_rockinrio.xpto.com.br;  # domínio real
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;                 # TLS terminado no Cloudflare
    proxy_read_timeout 60s;
    client_max_body_size 20m;
  }
}
sudo ln -s /etc/nginx/sites-available/api-rockinrio.conf /etc/nginx/sites-enabled/
sudo nginx -t            # valida a sintaxe
sudo systemctl reload nginx
Consistência de portas e limites. Alinhe HOST_PORT (.env), proxy_pass (Nginx) e a porta física livre na VPS. Além disso, client_max_body_size (20m) deve acompanhar MULTIPART_MAX_REQUEST_SIZE — senão uploads grandes tomam 413 no proxy antes de chegar à aplicação. A app confia em headers de proxy via server.forward-headers-strategy=NATIVE (RemoteIpValve), refletindo o IP real sem aceitar spoofing (rate-limit e auditoria).

12. Banco de dados e migrations SQL

As migrations NÃO são aplicadas pelo pipeline. A aplicação roda com spring.jpa.hibernate.ddl-auto=validate em produção — o Hibernate valida que o schema bate com as entidades, mas não cria nem altera tabelas. Os scripts scripts/0XX_*.sql devem ser aplicados manualmente ao MySQL, em ordem numérica, antes de subir a versão que os requer. Se o schema divergir, a aplicação não inicia.

Os scripts vão de 018_Fluxo_Processos_Documento.sql a 056_Auditoria_Snapshots_Completos.sql (numeração incremental). Contêm DDL (tabelas, índices, FKs), seeds e correções. Aplicar na ordem do número, cada um uma única vez.

  1. Backup antes de qualquer alteração: mysqldump achados_perdidos > backup_$(date +%F).sql
  2. Identifique o último script já aplicado (mantenha um registro/tabela de controle).
  3. Aplique os novos em ordem: mysql achados_perdidos < scripts/0XX_*.sql
  4. Só então faça o merge/push que dispara o deploy da nova versão.
Regra de ouro: migration primeiro, deploy depois. Como o deploy é automático no push para main/develop, aplique o SQL no banco antes do merge. Caso contrário, o novo container falha na validação de schema e entra em loop de restart.

13. Procedimento de bootstrap (primeiro deploy)

Execute uma única vez ao preparar um ambiente novo (dev ou prod). Depois, os deploys são automáticos via push.

  1. Provisionar a VPS: Docker Engine 24+, Compose v2, MySQL 8 acessível, Nginx.
  2. Registrar o GitLab Runner com a tag deploy, com acesso ao Docker daemon e ao diretório de deploy.
  3. Criar o diretório: sudo mkdir -p /opt/rockinrio-backend
  4. Criar o banco (CREATE DATABASE achados_perdidos;) e aplicar as migrations 018…056 em ordem (§12).
  5. Criar o .env em /opt/rockinrio-backend/.env a partir do .env.example, com valores REAIS:
JWT_SECRET=$(openssl rand -base64 48)
RESOURCE_ID_SECRET=$(openssl rand -base64 48)
DB_PASSWORD=<senha real do MySQL>
SPRINGDOC_ENABLED=false                 # produção
CORS_ALLOWED_ORIGINS=https://painel_rockinrio...,https://app_rockinrio...
CORS_ALLOWED_ORIGIN_PATTERNS=           # vazio em produção
HOST_PORT=8203                          # produção
  1. Definir a senha do admin (BCrypt) no banco: UPDATE usuario SET NM_Senha='$2a$10$...' WHERE NM_Login='admin';
  2. Configurar o Nginx (§11) e recarregar.
  3. Disparar o primeiro deploy: push/merge para develop (dev) ou main (prod).
  4. Validar (§15): docker compose ps (esperado healthy), logs, e curl ao /actuator/health através do Nginx.
Checklist de sanidade pré-primeiro-deploy. .env existe com JWT/RESOURCE secrets ≥32 chars · banco criado e migrations aplicadas · MySQL alcançável via host.docker.internal · porta HOST_PORT livre · Nginx apontando para a porta certa · runner com tag deploy online.

14. Deploy contínuo, rollback e limpeza

14.1 Deploy contínuo (dia a dia)

  1. (Se houver mudança de schema) aplicar migrations no banco — §12.
  2. git push para develop → deploy automático em Development.
  3. Após validação em dev, merge para main → deploy automático em Production.
  4. Acompanhar o job de deploy no GitLab e a saída de docker compose ps (status healthy).

14.2 Rollback

O pipeline não tem botão de rollback nativo; use uma das estratégias:

EstratégiaComoQuando
Revert de commitgit revert <sha> + push → redeploy da versão anteriorRegressão de código; forma mais limpa
Re-run de pipeline antigoNo GitLab, re-executar o pipeline de um commit estável anteriorQuando o código anterior já passou pelo gate
Imagem CI anteriordocker tag rockinrio-backend:ci-<sha_antigo> … e subir manualmenteEmergência; a imagem ainda existe (cleanup mantém as 3 últimas)
Rollback e banco. Se o release avançou o schema, o rollback de código pode falhar na validação contra o schema novo. Migrations idealmente são retrocompatíveis (aditivas). Reverter schema exige script de down manual e backup — planeje antes.

14.3 Limpeza automática pós-deploy

scripts/ci-docker-cleanup.sh roda ao fim de todo deploy: remove containers parados >24h e imagens dangling; mantém as KEEP_CI_IMAGES (default 3) imagens ci-* mais recentes; poda cache de build >168h e redes órfãs. Nunca remove volumes nem imagens em uso — uploads e banco estão seguros.

15.3 Onde olhar primeiro

  1. Log do job GitLab — falha de build/test/deploy.

16. Checklist operacional e hardening

16.1 Checklist antes de cada release em produção

  • Migrations necessárias aplicadas ao banco de produção (em ordem).
  • Backup do banco realizado.
  • SPRINGDOC_ENABLED=false no .env de produção.
  • CORS_ALLOWED_ORIGINS só com domínios reais; patterns de localhost vazios.
  • Gate de teste verde no pipeline.
  • Findings de segurança triados (Trivy/Semgrep/Gitleaks).
  • Health check healthy após subir (docker compose ps).
  • Janela de baixo tráfego (há downtime no down/up).
  • Plano de rollback definido (revert vs. imagem anterior).
